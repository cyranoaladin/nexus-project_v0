Rappel : ce que sait déjà une classe

reactivation Chaque instance possède ses propres attributs, créés par __init__. Une méthode comme ajouter modifie l’instance sur laquelle on l’appelle, et rien d’autre.

Quel est le nom de la classe ?

Réponse attendue : Boite

On déclare une classe avec le mot-clé class, suivi de son nom : ici Boite. __init__ et ajouter sont des méthodes ; contenu est un attribut.

  • __init__ — __init__ est une méthode spéciale (le constructeur) définie dans la classe, mais ce n’est pas la classe.
  • contenu — contenu est un attribut : une variable attachée à chaque instance.
  • ajouter — ajouter est une méthode : une fonction définie dans la classe.

Quel est l’attribut d’instance de Boite ?

Réponse attendue : self.contenu

Un attribut d’instance se crée avec self.nom = ... dans __init__ : ici self.contenu. b1 est une instance, valeur est un paramètre.

  • ajouter — ajouter est une méthode, pas une donnée.
  • b1 — b1 est une instance de la classe (un objet), pas un attribut.
  • valeur — valeur est un simple paramètre de la méthode ajouter.

Que fait l’appel b1.ajouter(5) ?

Réponse attendue : Il modifie la list contenu de b1 et ne renvoie rien

ajouter agit par mutation : elle modifie l’attribut contenu de l’instance sur laquelle on l’appelle. Elle ne contient pas de return, donc elle renvoie None.

  • Il renvoie une nouvelle boîte qui contient 5 — Aucun return, aucune nouvelle boîte n’est créée : b1 est modifiée sur place.
  • Il affiche 5 à l’écran — Il n’y a aucun print dans la méthode : rien n’est affiché.
  • Il modifie à la fois b1 et b2 — ajouter ne touche que l’instance sur laquelle on l’appelle (b1).

Après ces instructions, que contient b2.contenu ?

Réponse attendue : []

Chaque instance a sa propre list : __init__ en crée une nouvelle à chaque Boite(). b1.ajouter(5) ne modifie que celle de b1.

  • [5] — b2 n’a pas été modifiée : la list de b1 est un autre objet.
  • Une erreur — Aucune erreur : b2.contenu existe depuis le Boite() de b2.
  • None — contenu vaut bien une list (vide), pas None.

En une phrase : pourquoi b2.contenu n’est-il pas modifié par b1.ajouter(5) ?

Réponse attendue : Chaque appel Boite() exécute __init__, qui crée une NOUVELLE list pour cette instance. b1.contenu et b2.contenu sont deux objets distincts : ajouter à l’un ne modifie pas l’autre.

Liste, pile, file : trois façons d’organiser des données

types-abstraits Liste, pile et file se distinguent par la règle d’accès : n’importe où (liste), au sommet seulement (pile, LIFO), entrée d’un côté et sortie de l’autre (file, FIFO). Une interface se décrit sans parler de l’implémentation.

On empile A, puis B, puis C. Quel élément sera dépilé en premier ?

Réponse attendue : C

Dernier entré, premier sorti : C a été empilé en dernier, c’est donc le sommet, et il sort le premier.

  • A — A est au fond de la pile : il sortirait en dernier.
  • B — B est sous C : il sort après lui.
  • On ne peut pas le savoir — Si : la règle LIFO détermine l’ordre de sortie sans ambiguïté.

On enfile A, puis B, puis C. Quel élément sortira en premier ?

Réponse attendue : A

Premier entré, premier sorti : A est arrivé le premier, il sort le premier.

  • B — B passe après A.
  • C — C est le dernier arrivé : c’est le comportement d’une pile, pas d’une file.
  • Cela dépend de la taille — La taille ne change rien : la règle FIFO fixe l’ordre.

Pourquoi une pile ne propose-t-elle pas d’opération « lire l’élément de rang i » comme le fait une liste ?

Réponse attendue : Parce que la contrainte (n’agir qu’au sommet) fait partie de sa définition : c’est elle qui garantit le comportement LIFO

Une interface restreinte est un choix de conception : en limitant l’accès au sommet, on garantit la règle LIFO. Si on autorisait de lire ou d’insérer n’importe où, ce ne serait plus une pile.

  • Parce que Python l’interdit — Python n’interdit rien : c’est la définition de la structure qui limite les opérations.
  • Parce que ce serait beaucoup trop lent — La vitesse n’est pas la raison : même rapide, un accès au rang i ferait sortir de la règle LIFO.
  • Parce qu’une pile n’a pas d’indices en mémoire — Peu importe la mémoire : on parle ici d’interface, pas d’implémentation.

Une pile est réalisée avec une list Python. Que peut-on en conclure ?

Réponse attendue : La list est un choix de représentation : l’interface de la pile n’en dépend pas

La list est ici l’implémentation. L’interface (empiler, depiler, sommet…) ne change pas si l’on choisit une autre représentation.

  • Une pile et une list sont le même type abstrait — Non : le type abstrait pile impose une règle (LIFO) que list n’impose pas.
  • L’interface de la pile est celle de list : on peut utiliser tous les crochets — Non : celui qui utilise la pile n’a pas à connaître les crochets, seulement ses opérations.
  • Une pile ne peut être réalisée qu’avec une list — Non : on pourrait réaliser une pile autrement (autre représentation).

Avec tes mots : quelle est la différence entre l’interface et l’implémentation d’une pile ?

Réponse attendue : L’interface est ce que l’on peut demander à la pile (empiler, dépiler, consulter le sommet) et le comportement attendu (LIFO). L’implémentation est la manière de le réaliser : une list, une deque, des maillons… L’utilisateur n’en dépend pas.

Construire une classe Liste

liste Une classe cache sa représentation (_elements) derrière une interface. Un cas limite (indice invalide) se règle par une convention claire et unique : ici, IndexError.

À la fin du programme, que vaut L.longueur() ?

Réponse attendue : 2

Deux appels à ajouter : la liste contient "Ada" et "Alan", donc longueur() vaut 2.

  • 0 — La liste n’est pas vide : deux éléments ont été ajoutés.
  • 1 — Il y a eu deux ajouts, pas un.
  • Une erreur — Aucune erreur : tout est valide.

Que renvoie L.element(1) ?

Réponse attendue : "Alan"

Les indices commencent à 0 : element(0) est "Ada", element(1) est "Alan".

  • "Ada" — "Ada" a l’indice 0, pas 1.
  • 1 — 1 est l’indice, pas l’élément.
  • IndexError — L’indice 1 existe (la liste a deux éléments).

Pourquoi vaut-il mieux lever IndexError que renvoyer None quand l’indice est invalide ?

Réponse attendue : None peut être une valeur réellement stockée : on ne distinguerait plus « indice invalide » de « élément None ». Une exception signale l’erreur là où elle se produit et ne peut pas passer inaperçue.

Solution de référence

class Liste:
    def __init__(self):
        self._elements = []

    def est_vide(self):
        return len(self._elements) == 0

    def longueur(self):
        return len(self._elements)

    def ajouter(self, valeur):
        self._elements.append(valeur)

    def element(self, indice):
        if indice < 0 or indice >= len(self._elements):
            raise IndexError("indice invalide")
        return self._elements[indice]

L = Liste()
L.ajouter("Ada")
L.ajouter("Alan")
print(L.longueur())
print(L.element(1))

Erreurs probables

  • Oublier d’initialiser _elements dans __init__ (AttributeError dès le premier appel).
  • Accepter les indices négatifs (list[-1] « marche » en Python, mais le contrat de Liste les déclare invalides).
  • Renvoyer None au lieu de lever IndexError pour un indice invalide.
  • Écrire return dans ajouter (le contrat dit : ne rien renvoyer).

Contrôles automatiques

  • __init__ et est_vide : une liste neuve est vide
  • ajouter et longueur
  • element : lecture par indice
  • element : indice invalide → IndexError
  • Plusieurs listes indépendantes

Construire une Pile

pile Une pile obéit à LIFO. depiler() renvoie ET modifie ; sommet() consulte seulement. La même convention (IndexError) vaut pour toute structure vide.

Après empiler "A", "B", "C", que renvoie p.depiler() ?

Réponse attendue : "C"

Dernier entré, premier sorti : "C" est au sommet. depiler() le renvoie.

  • "A" — "A" est tout en bas.
  • "B" — "B" est sous "C".
  • Rien — depiler() renvoie l’élément retiré.

Juste après ce dépilage, que renvoie p.sommet() ?

Réponse attendue : "B"

Une fois "C" retiré, le sommet est "B". Si tu as répondu "C", tu as oublié que depiler() modifie la pile.

  • "A" — "A" est sous "B".
  • "C" — "C" a été retiré de la pile par depiler().
  • Une erreur — La pile contient encore "A" et "B" : pas d’erreur.

Et p.taille() ?

Réponse attendue : 2

Trois empilements, un dépilage : il reste "A" et "B", donc 2.

  • 1 — Il reste deux éléments, pas un.
  • 3 — 3 serait la taille avant le dépilage.
  • 0 — La pile n’est pas vide.

Un programme appelle depiler() sur une pile vide. Quelle politique est la plus sûre dans ce TP ?

Réponse attendue : Lever IndexError : l’erreur est signalée tout de suite

Lever une exception signale le problème à l’endroit où il se produit. None pourrait être confondu avec une vraie valeur empilée, et 0 aussi.

  • Renvoyer None sans rien dire — None peut être une valeur légitime stockée dans la pile : on ne distinguerait plus « pile vide » de « None au sommet ».
  • Ne rien vérifier et espérer que ça n’arrive pas — C’est une précondition sans garde-fou : le bug apparaîtrait plus tard, ailleurs.
  • Renvoyer 0 — 0 est une valeur possible comme une autre : même défaut que None.

Compare les trois politiques pour depiler() sur une pile vide (None, exception, précondition) et justifie celle du TP.

Réponse attendue : None : simple mais ambigu (None peut être empilé) et l’erreur apparaît plus tard, ailleurs. Exception : explicite et immédiate, c’est le choix du TP (IndexError). Précondition : exige que tout appelant teste est_vide() ; un oubli donne un bug silencieux.

Solution de référence

class Pile:
    def __init__(self):
        self._elements = []

    def est_vide(self):
        return len(self._elements) == 0

    def taille(self):
        return len(self._elements)

    def empiler(self, valeur):
        self._elements.append(valeur)

    def sommet(self):
        if self.est_vide():
            raise IndexError("pile vide")
        return self._elements[-1]

    def depiler(self):
        if self.est_vide():
            raise IndexError("pile vide")
        return self._elements.pop()

p = Pile()
p.empiler("A")
p.empiler("B")
p.empiler("C")
print(p.depiler())
print(p.sommet())
print(p.taille())

Autre implémentation valide (représentation inversée)

class Pile:
    def __init__(self):
        self._elements = []

    def est_vide(self):
        return self._elements == []

    def taille(self):
        return len(self._elements)

    def empiler(self, valeur):
        self._elements.insert(0, valeur)

    def sommet(self):
        if not self._elements:
            raise IndexError("pile vide")
        return self._elements[0]

    def depiler(self):
        if not self._elements:
            raise IndexError("pile vide")
        return self._elements.pop(0)

Erreurs probables

  • Confondre sommet() et depiler() : sommet ne doit pas retirer.
  • Ne pas retirer dans depiler (return self._elements[-1]).
  • Mélanger les extrémités : empiler à la fin mais dépiler au début (comportement FIFO).
  • Utiliser un attribut de classe partagé (une seule list pour toutes les piles).

Contrôles automatiques

  • est_vide et taille : une pile neuve est vide
  • empiler : la taille augmente
  • sommet : consulte sans retirer
  • depiler : renvoie ET retire
  • LIFO : dernier entré, premier sorti
  • Pile vide : sommet et depiler lèvent IndexError
  • Plusieurs piles indépendantes

Construire une File

file Une file obéit à FIFO. defiler() renvoie ET modifie ; premier() consulte seulement. Le choix de la représentation (début ou fin de list) n’est pas visible dans l’interface.

On enfile Adam, Alexandre, Zaineb. Qui est défilé en premier ?

Réponse attendue : Adam

Premier entré, premier sorti : Adam est arrivé le premier, il sort le premier.

  • Alexandre — Alexandre passe après Adam.
  • Zaineb — Zaineb est la dernière arrivée : ce serait le comportement d’une pile.
  • On ne peut pas savoir — La règle FIFO fixe l’ordre.

Après ce défilage, qui est le premier de la file ?

Réponse attendue : Alexandre

Adam est sorti (defiler modifie la file). Le prochain à sortir est Alexandre.

  • Adam — Adam a été retiré par defiler().
  • Zaineb — Zaineb est derrière Alexandre.
  • La file est vide — Il reste deux personnes.

Pourquoi dit-on que pop(0) est simple mais pas optimale ?

Réponse attendue : Elle décale tous les éléments restants d’un cran

Retirer en tête d’une list oblige Python à décaler les éléments suivants : plus la file est longue, plus c’est coûteux.

  • Elle n’existe pas pour les list — pop(0) existe bien.
  • Elle ne renvoie pas l’élément retiré — pop(0) renvoie bien l’élément retiré.
  • Elle retire le dernier élément — pop() sans argument retire le dernier ; pop(0) retire le premier.

Dans ta list, à quelle extrémité as-tu placé l’élément qui sortira en premier ? Explique ton choix.

Réponse attendue : Réponse libre. Exemple : « premier à sortir au début de la list, car pop(0) le retire directement et premier() lit _elements[0] ». Accepter aussi la représentation inversée (insert(0, …) et pop()), à condition que l’élève explique que l’interface n’en est pas affectée.

Pile ou file : même entrée, sorties différentes

comparer Pile : ajout et retrait au même endroit (LIFO). File : ajout à l’arrière, retrait à l’avant (FIFO). Sur A, B, C, D : la pile sort D, C, B, A ; la file sort A, B, C, D.

On empile A, B, C, D ; on dépile deux fois ; on empile E ; puis on dépile tout. Dans quel ordre sortent les éléments ?

Réponse attendue : D, C, E, B, A

Les deux premiers dépilages donnent D puis C. La pile contient alors A, B ; E arrive au sommet, donc le dépilage final donne E, B, A. Ordre total : D, C, E, B, A.

  • D, C, A, B, E — Après C, la pile contient A, B, puis E : E sort avant B et A.
  • A, B, C, D, E — C’est l’ordre d’arrivée : celui d’une file.
  • D, C, B, A, E — E est empilé après les deux dépilages : il est au sommet et sort avant B et A.

Dans une file, la suite des sorties est-elle toujours dans l’ordre d’arrivée, quelles que soient les alternances d’ajouts et de retraits ?

Réponse attendue : Oui : un élément sort toujours après tous ceux arrivés avant lui

C’est la définition de FIFO : l’ordre relatif des éléments est conservé, quel que soit le moment où l’on défile.

  • Non : cela dépend du nombre d’éléments — Le nombre d’éléments ne change pas la règle.
  • Non, sauf si on défile au moins deux fois de suite — Le nombre de défilages consécutifs ne change pas la règle.
  • Oui, mais seulement si la file n’a jamais été vide — Que la file ait été vide ou non ne change pas la règle.

Pile : où ajoute-t-on ?

Réponse attendue : Au sommet.

Pile : où retire-t-on ?

Réponse attendue : Au sommet (au même endroit que l’ajout).

Pile : quelle politique (LIFO ou FIFO) ?

Réponse attendue : LIFO (dernier entré, premier sorti).

File : où ajoute-t-on ?

Réponse attendue : À l’arrière (à l’entrée).

File : où retire-t-on ?

Réponse attendue : À l’avant (à la sortie).

File : quelle politique (LIFO ou FIFO) ?

Réponse attendue : FIFO (premier entré, premier sorti).

Ordre de sortie de la pile (A, B, C, D ajoutés dans cet ordre)

Réponse attendue : D, C, B, A.

Ordre de sortie de la file (A, B, C, D ajoutés dans cet ordre)

Réponse attendue : A, B, C, D.

Mission : le centre d’impression Nexus

mission Une structure se choisit selon la règle d’accès voulue : FIFO pour traiter dans l’ordre d’arrivée, LIFO pour revenir en arrière. Un objet peut contenir une structure et lui déléguer le travail.

Pour annuler les réglages dans l’ordre inverse de leur application, quelle structure convient ?

Réponse attendue : Une pile

Le dernier réglage appliqué doit être le premier annulé : c’est LIFO, donc une pile.

  • Une file — Une file annulerait d’abord le plus ancien réglage : pas ce qu’on veut.
  • Une liste indexée par rang — Possible mais inutilement général : la règle voulue est exactement celle d’une pile.
  • Aucune : il faut tout recalculer — Il suffit de mémoriser l’ancienne valeur à chaque modification.

En une phrase : pourquoi l’historique d’annulation est-il une pile, alors que le centre d’impression est une file ?

Réponse attendue : Les documents doivent être traités dans l’ordre d’arrivée (FIFO) : file. Une annulation doit défaire d’abord la dernière action (LIFO) : pile.

class FileImpression:
    def __init__(self):
        self._attente = File()

    def soumettre(self, document):
        self._attente.enfiler(document)

    def prochain(self):
        return self._attente.premier()

    def imprimer(self):
        return self._attente.defiler()

    def en_attente(self):
        return self._attente.taille()

    def est_vide(self):
        return self._attente.est_vide()


class Reglages:
    def __init__(self):
        self._valeurs = {"copies": 1, "couleur": "noir"}
        self._historique = Pile()

    def valeur(self, nom):
        return self._valeurs[nom]

    def regler(self, nom, valeur):
        self._historique.empiler((nom, self._valeurs[nom]))
        self._valeurs[nom] = valeur

    def annuler(self):
        nom, ancienne = self._historique.depiler()
        self._valeurs[nom] = ancienne

centre.soumettre("DS_Maths.pdf")
centre.soumettre("TP_NSI.pdf")
centre.soumettre("Correction.pdf")

print(centre.imprimer())
print(centre.en_attente())

options.regler("couleur", "bleu")
options.annuler()

print(options.valeur("copies"))

  • Empiler l’ancienne valeur seule, sans le nom du réglage : on ne sait plus quoi restaurer.
  • Modifier la valeur AVANT de mémoriser l’ancienne : l’ancienne valeur est perdue.
  • Utiliser une file pour l’historique d’annulation (annule le plus ancien réglage).

Quelle structure pour quelle situation ?

synthese Une pile ou une file se définit par ses opérations et leur comportement, pas par la manière de les réaliser : c’est ce qui en fait des types abstraits de données.

Le bouton « Annuler » d’un éditeur de texte

Pourquoi popleft est-il plus efficace que pop(0) sur une list ?

Réponse attendue : Il retire à l’extrémité gauche sans décaler tous les autres éléments

Une deque est conçue pour des ajouts et retraits aux deux extrémités sans décalage.

  • Il ne retire rien — Il retire bien l’élément le plus à gauche.
  • Il trie les éléments — Aucun tri n’est effectué.
  • Il copie la file entière — Il ne copie rien.

Ton interface File a-t-elle changé en passant de list à deque ? Qu’est-ce que cela montre ?

Réponse attendue : Non : les méthodes et leur comportement sont identiques. Seule l’implémentation change ; c’est tout l’intérêt d’un type abstrait de données.

Solution de référence

from collections import deque


class FileDeque:
    def __init__(self):
        self._elements = deque()

    def est_vide(self):
        return len(self._elements) == 0

    def taille(self):
        return len(self._elements)

    def enfiler(self, valeur):
        self._elements.append(valeur)

    def premier(self):
        if self.est_vide():
            raise IndexError("file vide")
        return self._elements[0]

    def defiler(self):
        if self.est_vide():
            raise IndexError("file vide")
        return self._elements.popleft()


f = FileDeque()
f.enfiler("A")
f.enfiler("B")
print(f.defiler())
print(f.taille())

Erreurs probables

  • Utiliser pop() au lieu de popleft() (comportement LIFO).
  • Oublier de tester la file vide : popleft lève IndexError avec un autre message.

Contrôles automatiques

  • FileDeque : taille, premier et est_vide
  • FileDeque : FIFO
  • FileDeque : file vide → IndexError

Points de vigilance

  • Le mot « liste » : type abstrait (collection ordonnée avec interface) ≠ list de Python (type concret). Une pile réalisée avec une list n’est pas « une list ».
  • Une seule convention de cas limite dans tout le TP : IndexError. L’annoncer dès l’étape Liste.
  • Les contrôles automatiques vérifient le COMPORTEMENT, pas le code : une pile dont le sommet est au début de la list est correcte.
  • Les restrictions de l’éditeur (noms commençant par un double tiret bas refusés, sauf __init__ et __len__ ; import interdit sauf collections.deque au bonus) sont pédagogiques, pas un dispositif de sécurité.
  • Rythme : si la classe est en retard à la 75e minute, passer directement à la mission en s’appuyant sur les classes fournies ; la synthèse peut se faire à l’oral.
