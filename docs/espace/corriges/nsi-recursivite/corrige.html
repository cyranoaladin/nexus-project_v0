Corrigé enseignant — Récursivité et programmation récursive

Terminale · NSI · Algorithmique et programmation · séance guidée de 1 h 50 à 2 h. Le parcours vérifie le comportement du code et son caractère récursif ; ce document donne les solutions de référence, les traces d’exécution, les réponses attendues, les erreurs probables et les interventions possibles.

Message central. Une fonction récursive résout un problème en traitant directement un cas simple, ou en le ramenant à une instance plus petite du même problème. Elle doit toujours progresser vers un cas de base. Cas de base + appel sur un problème plus petit + pile d’appels + retour des résultats + terminaison.
Position dans la progression NSI. Programmation orientée objet : TP POO 1 (Des objets qui agissent) et TP POO 2 (Listes, piles et files). Algorithmique et programmation : ce parcours. Il prolonge le TP Piles (pile d’appels, LIFO) sans être un « TP POO 3 ».

Diagnostic : comment un programme finit-il ?

diagnostic Une répétition finit parce que quelque chose progresse vers la condition d’arrêt. Sans progression, elle ne finit jamais : nous retrouverons cette exigence avec la récursivité.

Quelle est la condition d’arrêt de cette boucle ?

Réponse attendue : La boucle s’arrête quand n >= 0 devient fausse (n est alors négatif)

La boucle while continue tant que la condition n >= 0 est vraie ; elle s’arrête dès que n devient négatif.

  • La boucle s’arrête quand n vaut 3 — n vaut 3 au départ seulement : ce n’est pas ce qui arrête la boucle.
  • La boucle s’arrête après le premier print — print est dans la boucle : il est exécuté à chaque tour.
  • Il n’y a pas de condition d’arrêt — Toute boucle while possède une condition : ici n >= 0.

Quelle variable évolue à chaque tour de boucle ?

Réponse attendue : n

C’est n : la ligne n = n - 1 la diminue de 1 à chaque tour.

  • compte_a_rebours — compte_a_rebours est le nom de la fonction, il ne change pas.
  • print — print est une fonction d’affichage, pas une variable qui évolue.
  • La constante 0 — 0 est une valeur fixe, pas une variable.

Pourquoi cette boucle finit-elle toujours ?

Réponse attendue : Parce que n diminue de 1 à chaque tour, donc finit par devenir négatif

La boucle finit parce que n progresse vers la condition d’arrêt : il diminue de 1 à chaque tour.

  • Parce que Python arrête toute boucle au bout de dix tours — Python ne limite pas les boucles à dix tours : une boucle sans progression ne finirait jamais.
  • Parce que n est positif au départ — Être positif au départ ne suffit pas : il faut que n diminue.
  • Parce que print affiche des nombres — L’affichage n’a aucun rôle dans l’arrêt.

Que se passerait-il si la ligne n = n - 1 était supprimée ?

Réponse attendue : La boucle afficherait 3 indéfiniment : n ne changerait jamais

Sans cette ligne, n reste égal à 3 et la condition n >= 0 reste vraie : la boucle ne s’arrête jamais.

  • La boucle afficherait 3, 2, 1, 0 quand même — Sans diminution de n, la suite 3, 2, 1, 0 ne peut pas apparaître.
  • La boucle ne s’exécuterait jamais — La condition est vraie au départ : la boucle s’exécute.
  • Python refuserait de lire le programme — Le programme est syntaxiquement correct : c’est sa logique qui est défaillante.

En une phrase : à quelle condition une répétition finit-elle ?

Réponse attendue : Une répétition finit si, à chaque tour, quelque chose progresse vers la condition d’arrêt (ici n diminue jusqu’à devenir négatif). Sans progression, elle ne finit jamais.

Difficultés prévisibles

  • Confondre « la boucle s’arrête » et « la boucle fait ce qui est demandé » : insister sur la progression de la variable.

Interventions pédagogiques possibles

  • Faire exécuter la boucle à la main sur un tableau de variables.

Découvrir la récursivité

decouverte Une fonction récursive a un cas de base et un appel récursif sur un problème plus petit. Sans progression vers le cas de base, les appels s’empilent jusqu’à la RecursionError.

Quelle instruction est le cas de base de compte_a_rebours ?

Réponse attendue : if n < 0: return

Le cas de base est la situation la plus simple, traitée sans nouvel appel : quand n est négatif, on s’arrête.

  • print(n) — print(n) est exécuté pour chaque valeur de n ≥ 0 : ce n’est pas le cas d’arrêt.
  • compte_a_rebours(n - 1) — Cette ligne est l’appel récursif, pas le cas de base.
  • def compte_a_rebours(n): — C’est l’en-tête de la fonction : elle ne décide de rien.

Quelle instruction est l’appel récursif ?

Réponse attendue : compte_a_rebours(n - 1)

L’appel récursif est la ligne où la fonction s’appelle elle-même, ici sur un problème plus petit.

  • print(n) — print est un appel de fonction, mais pas un appel à compte_a_rebours elle-même.
  • if n < 0: return — Cette ligne arrête la récursion : c’est le cas de base.
  • def compte_a_rebours(n): — Ceci définit la fonction ; ce n’est pas un appel.

Pourquoi l’appel récursif porte-t-il sur n - 1 et non sur n ?

Réponse attendue : Parce que n - 1 est un problème plus petit : on se rapproche du cas de base

Avec n, on referait exactement le même problème, sans progresser : l’appel se répéterait sans fin. Avec n - 1, on se rapproche du cas de base n < 0.

  • Parce que Python interdit d’appeler une fonction avec la même valeur — Python n’interdit rien : c’est la logique qui l’exige.
  • Parce que print affiche n - 1 — print affiche n, pas n - 1.
  • Parce que n - 1 est toujours égal à 0 — n - 1 vaut 0 seulement quand n vaut 1.

Que va-t-il se passer si on exécute compte_a_rebours(3) avec cette version ?

Réponse attendue : Elle affiche 3 de nombreuses fois, puis Python s’arrête avec une RecursionError

Il n’y a ni cas de base ni progression : chaque appel recommence le même problème. Python limite la profondeur d’appels et signale une RecursionError.

  • Elle affiche 3 une fois, puis s’arrête — Rien n’arrête la fonction après le premier affichage : elle se rappelle.
  • Elle affiche 3, 2, 1, 0 — Elle ne décrémente jamais n : 2, 1, 0 n’apparaissent jamais.
  • Elle affiche 3 indéfiniment et ne s’arrête jamais, quoi qu’il arrive — En pratique, Python s’arrête de lui-même grâce à sa limite de profondeur.

Que signifie une RecursionError ?

Réponse attendue : Trop d’appels sont imbriqués : la limite de profondeur de la pile d’appels est dépassée

Chaque appel non terminé occupe de la place dans la pile d’appels. Quand il y en a trop, Python lève une RecursionError.

  • Python a trouvé une faute de syntaxe — Une faute de syntaxe donnerait une SyntaxError avant l’exécution.
  • La fonction a retourné None — Retourner None ne provoque aucune erreur par lui-même.
  • Le fichier du programme est trop gros — La taille du fichier n’a aucun lien avec cette erreur.

Explique en une phrase ce que tu as ajouté ou changé pour réparer compte_a_rebours.

Réponse attendue : J’ai ajouté un cas de base (if n < 0: return) pour arrêter la récursion, et j’ai remplacé l’appel compte_a_rebours(n) par compte_a_rebours(n - 1) pour que le problème diminue à chaque appel.

Solution de référence

def compte_a_rebours(n):
    if n < 0:
        return
    print(n)
    compte_a_rebours(n - 1)


compte_a_rebours(3)

Trace d’exécution

compte_a_rebours(2) → affiche 2 → compte_a_rebours(1) → affiche 1 → compte_a_rebours(0) → affiche 0 → compte_a_rebours(-1) → cas de base : return. Quatre appels empilés au maximum, puis les retours (sans valeur) remontent un à un.

Difficultés prévisibles

  • Penser que « la fonction s’appelle elle-même » suffit : un appel sans progression ni cas de base ne finit pas.
  • Croire que Python exécute réellement une infinité d’appels : la limite de profondeur provoque la RecursionError.

Erreurs probables dans le code

  • Cas de base placé après l’appel récursif (la fonction s’appelle avant de tester).
  • Appel sur n ou sur n + 1 au lieu de n - 1.
  • Cas de base n < 0 remplacé par n == 1 : le 0 n’est jamais affiché.

Interventions pédagogiques possibles

  • Demander à l’élève de prédire la sortie de la version défectueuse avant l’exécution ; lui faire lire le message de RecursionError.
  • Lui faire énoncer le cas de base à voix haute avant toute écriture.

Contrôles automatiques

  • compte_a_rebours(3) affiche 3, 2, 1, 0
  • Cas de base : rien à afficher pour n < 0
  • Terminaison : compte_a_rebours(50) se termine
  • La fonction s’appelle elle-même : un appel par valeur de n

Cas de base et appel récursif

cas-de-base Une fonction récursive se développe en une chaîne d’appels qui s’arrête au cas de base ; la valeur finale se construit avec les valeurs RETOURNÉES (return). La récurrence mathématique et la fonction récursive sont proches, mais distinctes.

Que retourne somme(0) ?

Réponse attendue : 0

C’est le cas de base : la somme des entiers de 1 à 0 est vide, donc 0. La fonction retourne 0 sans nouvel appel.

  • 1 — Il n’y a aucun entier à additionner : la somme est 0, pas 1.
  • None — Le cas de base contient bien return 0 : la fonction ne retourne pas None.
  • Une erreur — Aucune erreur : c’est le cas de base, traité directement.

Une fonction récursive en informatique et une suite définie par récurrence en mathématiques sont-elles la même chose ?

Réponse attendue : Non : les idées sont proches (un problème défini à partir d’un cas plus simple), mais l’une est un mécanisme d’exécution, l’autre une relation entre des nombres

Les deux définissent quelque chose à partir d’un cas plus simple, mais ce ne sont pas des notions identiques. Une fonction récursive peut d’ailleurs calculer les termes d’une suite définie par récurrence.

  • Oui : ce sont exactement deux écritures de la même notion — Elles sont proches, pas identiques : l’une est mathématique, l’autre est un programme qui s’appelle lui-même.
  • Non : une fonction récursive ne peut jamais calculer une suite — Au contraire : une fonction récursive peut très bien calculer les termes d’une suite.
  • Oui : mais seulement quand la fonction contient un print — Le print n’a aucun rapport avec cette distinction.

Avec cette version (le return est oublié devant n + somme(n - 1)), que renvoie somme(1) ?

Réponse attendue : None

La somme 1 + 0 est calculée puis jetée : sans return, la fonction ne renvoie rien, c’est-à-dire None. Pour somme(2), le calcul 2 + None provoquerait même une TypeError.

  • 1 — 1 serait la bonne valeur, mais elle n’est jamais renvoyée.
  • Une RecursionError — Les appels se terminent : le cas de base est bien atteint, il n’y a pas de RecursionError.
  • 0 — Le cas de base n’est pas utilisé par somme(1) : il l’est par l’appel somme(0), dont la valeur est jetée.

Dans la version qui contient print(n + somme(n - 1)), pourquoi somme(3) ne permet-elle pas d’obtenir la valeur 6 dans un calcul ?

Réponse attendue : Parce que print affiche une valeur mais ne la transmet pas à l’appelant : la fonction ne retourne rien

print montre une valeur à l’écran ; return la transmet à l’appelant. Une fonction récursive a besoin du résultat de l’appel plus petit pour construire le sien : il faut donc return.

  • Parce que print est interdit dans une fonction récursive — Aucune règle n’interdit print : le problème est qu’il ne transmet rien.
  • Parce que print ralentit trop la fonction — La vitesse n’est pas en cause.
  • Parce que print convertit tous les nombres en texte — print ne renvoie pas une chaîne : il ne renvoie rien du tout (None).

Que vaut somme(1) ?

Réponse attendue : 1.

Développe somme(4), ligne par ligne, comme pour somme(3).

Réponse attendue : somme(4) = 4 + somme(3) = 4 + 3 + somme(2) = 4 + 3 + 2 + somme(1) = 4 + 3 + 2 + 1 + somme(0) = 10. Accepter tout développement cohérent qui s’arrête à somme(0).

Que vaut somme(4) ?

Réponse attendue : 10.

Trace d’exécution

somme(3) → 3 + somme(2) → 3 + 2 + somme(1) → 3 + 2 + 1 + somme(0) → somme(0) retourne 0 → somme(1) retourne 1 → somme(2) retourne 3 → somme(3) retourne 6.

Difficultés prévisibles

  • Confondre afficher et retourner.
  • Ne pas voir que le return du cas de base est la seule source de valeur : les autres retours s’appuient dessus.
  • Assimiler récursivité et récurrence mathématique.

Interventions pédagogiques possibles

  • Faire développer somme(2), puis somme(3), à la main, sans ordinateur.
  • Faire corriger le programme sans return en lisant la valeur obtenue (None).

Suivre la pile d’appels

pile-appels Une fonction récursive empile ses appels pendant la descente, puis les termine dans l’ordre inverse pendant la remontée : le dernier appel créé est le premier terminé, comme dans une pile (LIFO).

Dans la trace de somme(4), quel appel se termine en premier ?

Réponse attendue : somme(0)

Le dernier appel créé, somme(0), est le premier à retourner sa valeur : tous les autres l’attendent.

  • somme(4) — somme(4) est le premier créé : il attend la fin de tous les autres.
  • somme(2) — somme(2) attend le résultat de somme(1), qui attend celui de somme(0).
  • Tous se terminent en même temps — Les appels se terminent un par un, dans l’ordre inverse de leur création.

Combien d’appels sont empilés en même temps, au maximum, pendant somme(4) ?

Réponse attendue : 5

Au plus bas de la descente, somme(4), somme(3), somme(2), somme(1) et somme(0) sont tous en attente : 5 appels.

  • 4 — Il faut compter aussi somme(0), le cas de base.
  • 1 — Un seul appel serait empilé si la fonction n’était pas récursive.
  • 10 — 10 est la valeur retournée, pas le nombre d’appels.

Pourquoi dit-on pile d’appels ?

Réponse attendue : Parce que le dernier appel créé est le premier terminé (LIFO), comme dans une pile

Dernier entré, premier sorti : c’est exactement la règle d’une pile. Le programmeur n’a pas à la coder : l’interpréteur s’en charge.

  • Parce que le premier appel créé est le premier terminé (FIFO) — Ce serait le comportement d’une file, pas d’une pile.
  • Parce que les appels sont triés par ordre alphabétique — Aucun tri alphabétique n’intervient.
  • Parce que Python stocke chaque appel dans une list que tu dois programmer — La pile d’appels est gérée par l’interpréteur : tu ne la programmes pas.

Dans la trace de puissance(2, 4), quelle valeur retourne puissance(2, 3) ?

Réponse attendue : 8

puissance(2, 3) = 2 × puissance(2, 2) = 2 × 4 = 8. C’est puissance(2, 4) qui retourne 16.

  • 16 — 16 est la valeur retournée par puissance(2, 4), l’appel initial.
  • 4 — 4 est la valeur retournée par puissance(2, 2).
  • 2 — 2 est la valeur retournée par puissance(2, 1).

Avec tes mots : quelle différence y a-t-il entre la descente dans les appels et la remontée des valeurs retournées ?

Réponse attendue : Pendant la descente, chaque appel en crée un nouveau sur un problème plus petit, jusqu’au cas de base : les appels s’empilent et aucune valeur n’est encore calculée. Pendant la remontée, chaque appel reçoit la valeur de l’appel plus petit, calcule la sienne et la retourne, du dernier appel créé au premier.

Solution de référence

def somme_trace(n, profondeur=0):
    marge = "  " * profondeur
    print(marge + "APPEL somme(" + str(n) + ")")
    if n == 0:
        resultat = 0
    else:
        resultat = n + somme_trace(n - 1, profondeur + 1)
    print(marge + "RETOUR " + str(resultat))
    return resultat


somme_trace(3)

Trace d’exécution

Affichage attendu de somme_trace(3) : APPEL somme(3) ; (2 espaces) APPEL somme(2) ; (4) APPEL somme(1) ; (6) APPEL somme(0) ; (6) RETOUR 0 ; (4) RETOUR 1 ; (2) RETOUR 3 ; RETOUR 6.

Difficultés prévisibles

  • Imaginer que les appels « se font en parallèle » ou que la valeur est connue dès la descente.
  • Mélanger l’ordre de création et l’ordre de fin des appels.

Erreurs probables dans le code

  • Oublier d’augmenter la profondeur dans l’appel récursif (tous les affichages sont alignés).
  • Afficher le RETOUR avant de connaître le résultat.
  • Appeler somme_trace(n - 1) sans profondeur + 1.

Interventions pédagogiques possibles

  • Utiliser la figure interactive pas à pas, en la masquant à moitié : l’élève prévoit la prochaine étape.
  • Faire le lien avec le TP Piles : « quel est le sommet ? ».

Contrôles automatiques

  • Les APPEL et RETOUR de somme_trace(3), avec leur retrait
  • somme_trace renvoie la même valeur que somme
  • Tous les APPEL précèdent tous les RETOUR (descente puis remontée)
  • Profondeur de la pile : n + 1 appels simultanés

Écrire ses premières fonctions récursives

ecrire Avant d’écrire : cas de base, réduction, terminaison, valeur retournée. Une fonction récursive correcte se reconnaît à ses valeurs, mais aussi au fait qu’elle s’appelle réellement elle-même sur un problème plus petit.

Quel est le défaut de la première fonction, f(n) qui retourne f(n - 1) ?

Réponse attendue : Elle n’a pas de cas de base : rien n’arrête les appels

Sans cas de base, chaque appel en crée un nouveau, indéfiniment : la limite de profondeur est dépassée et Python lève une RecursionError.

  • L’appel porte sur n au lieu de n - 1 — Ici l’appel porte bien sur n - 1 : c’est le cas de base qui manque.
  • Elle contient un print en trop — Il n’y a aucun print dans cette fonction.
  • Elle devrait être écrite avec une boucle — Une boucle n’est pas nécessaire : la récursion convient, mais il lui faut un cas de base.

Quel est le défaut de la deuxième fonction (cas de base n == 0, puis return f(n)) ?

Réponse attendue : L’appel récursif porte sur le même problème : aucune progression vers le cas de base

Pour n différent de 0, f(n) rappelle f(n) : exactement le même problème, sans jamais s’en rapprocher du cas de base.

  • Le cas de base est faux — Le cas de base est correct pour n == 0 : c’est l’appel qui ne progresse pas.
  • Il manque un return — Il y a bien un return dans chaque branche.
  • La fonction n’a pas de paramètre — La fonction a bien un paramètre, n.

Quel est le défaut de la troisième fonction (return f(n + 1), pour un appel f(3)) ?

Réponse attendue : n s’éloigne de 0 : le cas de base n’est jamais atteint

f(3) appelle f(4), puis f(5)… : on s’éloigne du cas de base n == 0 au lieu de s’en rapprocher. La fonction ne termine pas.

  • Le cas de base est incorrect — Le cas de base n == 0 est correct ; c’est l’appel qui s’en éloigne.
  • f(n + 1) est interdit par Python — Python n’interdit rien : c’est la logique qui est fausse.
  • La fonction termine mais retourne 0 — Elle ne termine pas : elle ne retourne jamais 0 pour n = 3.

Que vaut 0! ?

Réponse attendue : 1 (convention : le produit vide).

Quel est le cas de base de chacune des trois fonctions (somme, factorielle, puissance) ?

Réponse attendue : somme : n == 0, valeur 0. factorielle : n == 0, valeur 1. puissance : n == 0, valeur 1.

Comment chacune ramène-t-elle son problème à un problème plus petit ? Que fait-elle de la valeur retournée par l’appel récursif ?

Réponse attendue : somme(n) = n + somme(n - 1) ; factorielle(n) = n × factorielle(n - 1) ; puissance(a, n) = a × puissance(a, n - 1). La valeur retournée par l’appel plus petit est combinée avec n (ou a) pour construire la réponse.

Pour puissance(a, n) avec n ≥ 0, pourquoi les appels finissent-ils toujours ?

Réponse attendue : À chaque appel, n diminue de 1 ; comme n est un entier positif ou nul au départ, il finit par valoir 0, qui est le cas de base.

Solution de référence

def somme(n):
    if n == 0:
        return 0
    return n + somme(n - 1)


def factorielle(n):
    if n == 0:
        return 1
    return n * factorielle(n - 1)


def puissance(a, n):
    if n == 0:
        return 1
    return a * puissance(a, n - 1)


print(somme(4))
print(factorielle(5))
print(puissance(2, 4))

Autre implémentation valide

def somme(n):
    if n <= 0:
        return 0
    return somme(n - 1) + n


def factorielle(n):
    if n < 2:
        return 1
    return n * factorielle(n - 1)


def puissance(a, n):
    # Variante : on divise l’exposant par deux (moins d’appels).
    if n == 0:
        return 1
    moitie = puissance(a, n // 2)
    if n % 2 == 0:
        return moitie * moitie
    return a * moitie * moitie

Trace d’exécution

factorielle(4) → 4 × factorielle(3) → 4 × 3 × factorielle(2) → 4 × 3 × 2 × factorielle(1) → … × factorielle(0) → 1 ; remontée : 1, 1, 2, 6, 24.

Difficultés prévisibles

  • Écrire le code avant d’avoir identifié le cas de base.
  • Oublier la convention 0! = 1.
  • Écrire une version avec boucle qui donne les bonnes valeurs : le contrôle « s’appelle elle-même » le signale.

Erreurs probables dans le code

  • Cas de base oublié ou faux (0! = 0, a puissance 0 = 0).
  • Oublier return devant l’appel récursif (la fonction renvoie None).
  • Version avec boucle.
  • Appel récursif sur n au lieu de n - 1.

Interventions pédagogiques possibles

  • Faire remplir les champs cas de base / réduction avant l’éditeur.
  • Si l’élève bloque : lui faire écrire le développement d’un exemple, puis généraliser.

Contrôles automatiques

  • somme : cas de base somme(0) = 0
  • somme : somme(1), somme(3), somme(5), somme(10)
  • somme : la fonction s’appelle elle-même
  • factorielle : 0! = 1 et 1! = 1
  • factorielle : 3!, 5!, 6!
  • factorielle : la fonction s’appelle elle-même
  • puissance : cas de base a puissance 0 = 1
  • puissance : 2 puissance 1, 2 puissance 5, 3 puissance 3, 10 puissance 4
  • puissance : la fonction s’appelle elle-même
  • Terminaison : somme(100), factorielle(20) et puissance(2, 100) se terminent

Récursivité sur des chaînes et des listes

structures Une chaîne ou une liste se réduit en lui retirant un élément. Le cas de base est la structure vide (ou minimale) ; une tranche crée une copie, ce qui est lisible mais pas toujours le plus efficace.

Quel est le cas de base de longueur(texte) ?

Réponse attendue : texte est la chaîne vide : sa longueur est 0

La chaîne vide est la situation la plus simple : sa longueur est 0, sans nouvel appel. Sinon, on retire un caractère et on ajoute 1.

  • texte vaut "NSI" — "NSI" est un exemple d’appel, pas un cas de base général.
  • texte contient exactement un caractère et un seul — Un seul caractère se traite aussi par un appel sur la chaîne vide : ce n’est pas obligatoire comme cas de base.
  • Il n’y a pas de cas de base : on appelle toujours longueur — Sans cas de base, les appels ne s’arrêteraient jamais.

Pour est_palindrome, quels cas peut-on traiter directement, sans appel récursif ?

Réponse attendue : La chaîne vide et la chaîne d’un seul caractère : toujours vrai

Une chaîne vide ou d’un seul caractère se lit forcément pareil dans les deux sens : la réponse est True.

  • Seulement la chaîne vide — La chaîne d’un seul caractère est aussi un palindrome, et il est utile de la traiter directement.
  • Les chaînes de deux caractères — Pour deux caractères, il faut comparer le premier et le dernier.
  • Les chaînes qui commencent par une voyelle — La première lettre n’a aucune importance pour décider si un mot est un palindrome.

Si le premier et le dernier caractère sont égaux, que faut-il faire ensuite ?

Réponse attendue : Tester l’intérieur de la chaîne, c’est-à-dire sans ces deux caractères

Égaux aux deux bouts ne suffit pas : il faut que l’intérieur soit aussi un palindrome. C’est l’appel récursif, sur une chaîne plus courte.

  • Renvoyer True immédiatement — "abca" a le même premier et dernier caractère mais n’est pas un palindrome.
  • Inverser la chaîne — Inverser la chaîne ne serait pas récursif et n’est pas nécessaire.
  • Recommencer avec la même chaîne — Recommencer avec la même chaîne ne progresse pas vers le cas de base.

Que vaut somme_liste([]) ?

Réponse attendue : 0

La somme d’une liste vide est 0 : c’est le cas de base, et c’est aussi l’élément neutre de l’addition.

  • None — Le cas de base doit retourner une valeur, pas None.
  • 1 — 1 ajouterait un élément qui n’existe pas.
  • Une IndexError — Aucun accès à un indice n’est nécessaire pour une liste vide.

Que fait l’expression tab[1:] ?

Réponse attendue : Elle crée une nouvelle liste contenant tous les éléments sauf le premier

tab[1:] est une tranche : une nouvelle liste (copie) sans le premier élément. tab, elle, n’est pas modifiée.

  • Elle retire le premier élément de tab — Une tranche ne modifie pas tab : elle en crée une copie.
  • Elle renvoie l’indice 1 — tab[1] serait l’élément d’indice 1 ; avec « : », on obtient une liste.
  • Elle renvoie le premier élément — Le premier élément s’obtient avec tab[0].

Avant de coder : écris en français les trois situations que doit traiter est_palindrome (cas de base, désaccord, accord).

Réponse attendue : Si la chaîne est vide ou d’un seul caractère, c’est un palindrome (True). Sinon, si le premier et le dernier caractère sont différents, ce n’est pas un palindrome (False). Sinon, la réponse est celle de l’intérieur de la chaîne (sans ses deux extrémités).

Itératif ou récursif ?

iteratif Récursif et itératif sont deux écritures possibles. La récursivité suit la structure du problème mais empile des appels (coût, RecursionError) ; la boucle n’empile rien. Aucune n’est meilleure par principe.

factorielle_iterative(5) et factorielle_recursive(5) donnent-elles le même résultat ?

Réponse attendue : Oui : 120 dans les deux cas

Les deux calculent 5! = 120 : ce sont deux manières d’écrire le même calcul.

  • Non : la version récursive renvoie 24 — La version récursive renvoie bien 120.
  • Non : la version itérative renvoie None — La version itérative contient bien un return.
  • Cela dépend de la machine — Le résultat ne dépend pas de la machine.

Laquelle des deux versions utilise explicitement une boucle ?

Réponse attendue : La version itérative

La version itérative contient une boucle for ; la version récursive n’en contient aucune : la répétition vient des appels.

  • La version récursive — La version récursive répète grâce aux appels, pas à une boucle.
  • Aucune des deux — Il y a bien une boucle dans l’une des deux.
  • Les deux — La version récursive n’en a pas.

Laquelle des deux versions utilise la pile d’appels pour se répéter ?

Réponse attendue : La version récursive

Chaque appel récursif est empilé en attendant le résultat du suivant ; la boucle, elle, répète sans empiler.

  • La version itérative — La boucle reste dans un seul appel : rien n’est empilé.
  • Les deux de la même façon — Une seule des deux empile des appels.
  • Aucune des deux — Toute fonction appelée occupe un cadre dans la pile, et ici il y en a plusieurs pour la récursive.

Laquelle traduit le plus directement la définition n! = n × (n - 1)! avec 0! = 1 ?

Réponse attendue : La version récursive

La version récursive recopie la définition mathématique : cas de base 0! = 1, puis n! = n × (n - 1)!.

  • La version itérative — La version itérative calcule le produit 1 × 2 × … × n, ce qui est équivalent mais moins direct.
  • Aucune — Une des deux est plus proche de la définition.
  • Les deux au même niveau — Elles ne sont pas équivalentes en lisibilité par rapport à cette définition.

Pourquoi puissance_recursive(2, 1000) provoque-t-elle une RecursionError dans cet atelier alors que puissance_iterative(2, 1000) fonctionne ?

Réponse attendue : Parce que 1000 appels sont empilés en même temps et dépassent la limite de profondeur, alors que la boucle n’empile rien

La limite porte sur le nombre d’appels imbriqués. La version récursive en empile 1 001 ; la version itérative en utilise un seul.

  • Parce que 2 puissance 1000 est un nombre trop grand pour Python — Python sait calculer 2 puissance 1000 : le nombre n’est pas le problème.
  • Parce que la récursivité est interdite pour n ≥ 100 — Aucune interdiction de ce genre n’existe : c’est une limite de profondeur.
  • Parce que la boucle est plus rapide — La vitesse n’est pas en cause ici.

Une solution récursive est-elle toujours meilleure qu’une solution itérative ?

Réponse attendue : Non : on choisit selon la structure du problème et son coût

Ni l’une ni l’autre n’est automatiquement meilleure. Une structure naturellement récursive (dossiers imbriqués, arbres) s’écrit plus clairement en récursif ; un simple parcours s’écrit très bien avec une boucle.

  • Oui : elle est toujours plus courte — Plus courte n’est pas toujours plus claire ni plus efficace.
  • Oui : elle consomme moins de mémoire — La récursivité consomme au contraire de la mémoire (pile d’appels).
  • Non : l’itérative est toujours meilleure — L’itératif n’est pas toujours meilleur non plus : pour des structures imbriquées, le récursif est souvent plus naturel.

Donne un cas où tu choisirais plutôt une écriture récursive, et un cas où tu choisirais plutôt une boucle. Justifie.

Réponse attendue : Récursif : structure naturellement imbriquée (dossiers, arbres) ou définition mathématique récursive. Boucle : simple répétition, très grand nombre d’étapes (pas de pile d’appels, pas de RecursionError). Accepter toute justification cohérente.

    if n == 0:

    return a * puissance_recursive(a, n - 1)


def puissance_iterative(a, n):
    resultat = 1
    for _ in range(n):

    return resultat

Mission : explorer un dossier imaginaire

mission Une structure imbriquée se parcourt naturellement par récursivité : un élément simple est le cas de base, un élément composé se traite en traitant chacun de ses éléments.

Dans cette modélisation, comment distingue-t-on un fichier d’un dossier ?

Réponse attendue : Un fichier est une chaîne, un dossier est une liste

Un fichier est une chaîne (son nom) ; un dossier est une liste de fichiers et d’autres dossiers. On les distingue avec isinstance(x, list).

  • Un fichier est une liste, un dossier est une chaîne — C’est l’inverse : le dossier contient d’autres éléments, c’est donc la liste.
  • On ne peut pas les distinguer — On peut les distinguer par leur type, avec isinstance.
  • Un dossier est toujours un nombre — Un nombre ne représente ni l’un ni l’autre ici.

Pour compter_fichiers, quel est le cas de base ?

Réponse attendue : L’élément est un fichier (une chaîne) : il compte pour 1

Un fichier est le plus petit élément possible : il compte pour 1, sans nouvel appel. Un dossier vide se traite naturellement : 0 fichier.

  • L’élément est un dossier vide uniquement — Un dossier vide contient 0 fichier, mais ce n’est pas le seul cas simple : un fichier seul aussi.
  • Il n’y en a pas : on appelle toujours compter_fichiers — Sans cas de base, la récursion ne s’arrêterait jamais.
  • L’élément est le premier de la liste — La place dans la liste n’a pas de rôle dans le cas de base.

Dans compter_fichiers : quel est le cas de base, et sur quoi porte l’appel récursif ?

Réponse attendue : Cas de base : l’élément est un fichier (une chaîne), il compte pour 1. Appel récursif : sur chaque élément du dossier (fichier ou sous-dossier), dont on additionne les résultats.

Pour inverse(texte) : comment ramènes-tu le problème à un problème plus petit, et comment utilises-tu le résultat obtenu ?

Réponse attendue : On retire le premier caractère ; on inverse le reste (appel récursif, chaîne plus courte) ; le résultat est le reste inversé suivi du caractère retiré. Cas de base : la chaîne vide, qui s’inverse en elle-même.

Synthèse : ce qu’il faut retenir

synthese Cas de base + appel sur un problème plus petit + progression vers le cas de base : c’est ce qui rend une fonction récursive correcte. La pile d’appels garde les appels en attente ; le dernier créé est le premier terminé.

Que doit posséder toute fonction récursive correcte ?

Réponse attendue : Un cas de base, un appel sur un problème plus petit, et une progression vers le cas de base

Sans cas de base, les appels ne s’arrêtent pas ; sans problème plus petit, il n’y a pas de progression ; sans appel, la fonction n’est pas récursive.

  • Une boucle et un compteur — Une fonction récursive peut se passer de boucle : la répétition vient des appels.
  • Seulement un appel à elle-même — Un appel à elle-même seul ne suffit pas : il faut un arrêt et une progression.
  • Un print dans chaque branche — Le print n’a aucun rôle dans la correction d’une fonction récursive.

Dans f(3) → f(2) → f(1) → f(0), quel appel se termine le premier ?

Réponse attendue : f(0)

Le dernier appel créé, f(0), est le premier à se terminer : logique de pile (LIFO).

  • f(3) — f(3) est le premier créé : il se termine en dernier.
  • f(2) — f(2) attend le retour de f(1).
  • f(1) — f(1) attend le retour de f(0).

Pourquoi une fonction récursive correcte finit-elle ?

Réponse attendue : Parce qu’à chaque appel le problème diminue, jusqu’à atteindre le cas de base

La terminaison vient de la progression : si le problème diminue à chaque appel, il finit par atteindre le cas de base.

  • Parce que Python arrête toujours les fonctions au bout de quelques appels — Python ne sauve pas une fonction mal écrite : il lève une RecursionError.
  • Parce qu’elle retourne une valeur — Retourner une valeur ne garantit pas la fin des appels.
  • Parce qu’elle utilise return — return seul ne garantit pas non plus la fin.

Pour compter tous les fichiers d’un dossier contenant des sous-dossiers de profondeur quelconque, que choisis-tu en général ?

Réponse attendue : Une écriture récursive, car la structure est elle-même imbriquée

Un dossier contient des dossiers : la structure du problème est récursive, donc la solution récursive la traduit directement.

  • Une boucle for obligatoirement, la récursivité étant interdite — La récursivité n’est jamais interdite.
  • Une écriture récursive uniquement si le dossier est vide — Un dossier vide se traite par le cas de base, mais la récursivité sert surtout pour les dossiers imbriqués.
  • Aucune solution n’existe — La mission a justement montré une solution.

En quelques phrases, explique à un camarade qui découvre la récursivité comment on construit une fonction récursive.

Réponse attendue : Réponse libre. Attendu : chercher le cas le plus simple (cas de base), ramener le cas général à un problème plus petit (appel récursif), vérifier que le problème diminue (terminaison), puis construire la valeur retournée à partir de celle de l’appel plus petit.

Pour aller plus loin : dichotomie, Fibonacci et arbres

bonus La dichotomie divise le problème par deux à chaque appel. Une récursion à deux appels peut recalculer plusieurs fois les mêmes valeurs : correct ne veut pas dire efficace.

Dans indice_dicho, que doit-on renvoyer quand debut > fin ?

Réponse attendue : -1 : la plage est vide, x n’y est pas

Quand debut > fin, il ne reste plus aucune case à examiner : c’est le cas de base « non trouvé », et on renvoie -1.

  • 0 — 0 serait une position valide : on ne peut pas s’en servir pour dire « non trouvé ».
  • L’indice du milieu — Il n’y a plus de milieu quand la plage est vide.
  • None — None pourrait fonctionner dans l’absolu, mais l’énoncé demande -1.

Pourquoi la dichotomie est-elle bien plus rapide qu’une recherche case par case sur une grande liste triée ?

Réponse attendue : Parce qu’à chaque appel, la plage de recherche est à peu près divisée par deux

Diviser par deux à chaque appel : pour 1 000 cases, une douzaine d’appels suffisent, contre 1 000 au pire en parcourant tout.

  • Parce qu’elle trie la liste — La liste doit déjà être triée : la dichotomie ne trie rien.
  • Parce qu’elle ne regarde jamais le milieu — Elle regarde au contraire le milieu à chaque appel.
  • Parce qu’elle utilise moins de variables — Le nombre de variables n’intervient pas.

Une fonction peut-elle être correcte mais inefficace ?

Réponse attendue : Oui : fibonacci donne le bon résultat mais recalcule les mêmes valeurs un grand nombre de fois

Correction (le résultat est juste) et efficacité (le temps et la mémoire utilisés) sont deux qualités différentes.

  • Non : une fonction correcte est toujours efficace — Les deux qualités sont indépendantes.
  • Non : une fonction inefficace est toujours incorrecte — Une fonction inefficace peut donner un résultat tout à fait juste.
  • Oui, mais seulement si elle contient une boucle — Une boucle n’est pas nécessaire pour être inefficace.

Combien de fois peut-on diviser 1 000 par 2 avant d’arriver à 1 ? Que dit ce nombre sur le nombre d’appels de la dichotomie ?

Réponse attendue : Environ 10 fois (2 puissance 10 = 1 024). La dichotomie fait donc environ 10 à 11 appels pour 1 000 cases, au lieu de 1 000 cases examinées au pire.

Solution de référence

def maximum(tab):
    if len(tab) == 1:
        return tab[0]
    reste = maximum(tab[1:])
    if tab[0] > reste:
        return tab[0]
    return reste


def indice_dicho(tab, x, debut, fin):
    if debut > fin:
        return -1
    milieu = (debut + fin) // 2
    if tab[milieu] == x:
        return milieu
    if tab[milieu] < x:
        return indice_dicho(tab, x, milieu + 1, fin)
    return indice_dicho(tab, x, debut, milieu - 1)

print(indice_dicho([2, 5, 8, 12, 16, 23], 12, 0, 5))

Comment diagnostiquer une mauvaise compréhension ?

L’élève sait écrire la syntaxe mais ne comprend pas la récursion

Symptôme : il reproduit un modèle (if n == 0 … return n + f(n - 1)) sans pouvoir tracer somme(4), ni dire ce que retourne somme(1).

Intervention : Retirer l’ordinateur : lui faire développer somme(3) à la main, puis tracer la pile avec la figure interactive. Lui demander de prévoir la valeur de chaque RETOUR avant de la voir.

L’élève oublie le cas de base

Symptôme : RecursionError, ou fonction qui « marche presque ».

Intervention : Travailler d’abord le raisonnement, pas la syntaxe : « quel est le plus petit problème ? » Lui faire écrire en français la réponse à ce plus petit problème avant le code.

L’élève comprend la descente mais pas les retours

Symptôme : il sait où les appels vont, mais pas d’où vient la valeur finale ; il pense que « somme(4) vaut 4 » ou n’explique pas le rôle du return.

Intervention : Utiliser la pile d’appels visuelle : insister sur le fait que chaque appel attend la valeur de l’appel plus petit. Faire annoter chaque RETOUR avec le calcul (2 + 1 = 3).

L’élève confond afficher et retourner

Symptôme : print à la place de return, ou le contrôle indique « renvoie None ».

Intervention : Faire utiliser le résultat d’un appel dans un calcul (somme(3) + 1). Constater None, puis comparer avec print.

L’élève confond récursivité et récurrence mathématique

Symptôme : il cherche une « formule » plutôt qu’un appel de fonction, ou croit que toute suite définie par récurrence est une fonction récursive.

Intervention : Reprendre la distinction du cours : la récurrence relie des nombres ; la fonction récursive est un mécanisme d’exécution. Les faire coexister sur un exemple (somme).

L’élève veut tout faire avec des boucles

Symptôme : le contrôle « la fonction s’appelle elle-même » échoue, alors que les valeurs sont correctes.

Intervention : Valider d’abord l’exactitude, puis demander : « comment ce problème se ramène-t-il à lui-même, en plus petit ? » La mission des dossiers imbriqués rend la boucle difficile : bon contre-exemple.

Points de vigilance

  • Le parcours vérifie le COMPORTEMENT (valeurs de retour, affichages) et le caractère récursif (la fonction doit s’appeler elle-même), pas la forme exacte du code : toute écriture valide est acceptée.
  • La limite de profondeur est volontairement basse dans cet atelier (200 appels) : une RecursionError arrive vite et sans geler le navigateur. Python standard autorise environ 1 000 appels.
  • Les restrictions de l’éditeur (aucun import, pas d’accès fichier, pas d’exécution dynamique) sont pédagogiques, pas un dispositif de sécurité.
  • Fibonacci est volontairement absent du noyau : deux appels récursifs introduisent l’arbre d’appels et les recalculs, traités seulement en bonus comme contre-exemple.
  • On n’enseigne pas ici l’optimisation de la récursion terminale : Python ne la fait pas en pratique.
  • Rythme : si la classe est en retard à la 75e minute, passer à la mission avec la partie A seule (nombres imbriqués) ; la synthèse peut se faire à l’oral.
  • Le dernier contrôle de l’étape « Itératif ou récursif ? » (puissance_iterative(2, 1000)) doit réussir sans RecursionError : c’est le constat du coût de la pile d’appels.
