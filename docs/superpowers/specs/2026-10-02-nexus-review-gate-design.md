# Nexus Review Gate — bootstrap design

Date: 2026-10-02. Approved scope: a free, private GitHub App replaces routine human PR approval; this document does not authorize a live ruleset change.

## Trust boundary

The private, user-owned `Nexus Review Gate` App (ID `5166727`, slug `nexus-review-gate`) is installed only on `cyranoaladin/nexus-project_v0` (installation `167301397`). The installation shows **Metadata read and Checks write only**; it has no Contents, Pull requests, Actions, administration, deployment, or secrets write permission. Its installation token is used only to publish the `Nexus Review Gate` Check Run. PR, diff, review, thread, and check reads use a distinct read-only `GITHUB_TOKEN`. A future ruleset must bind the context to integration ID `5166727`. GitHub Actions can emit a same-named check as `github-actions` (app ID `15368`); that is not the same source. The security claim is App source binding plus trusted workflow and secret isolation—not that Actions cannot use the name.

## Foundation checkpoint (current bootstrap PR)

The first increment proves the App identity chain only. The official `actions/create-github-app-token` v3.2.0 action is pinned at `bcd2ba49218906704ab6c1aa796996da409d3eb1`, uses the configured Client ID and private key, asks for `permission-checks: write`, and scopes the token to this repository by omitting owner/repositories. Its post-step revokes the token. The trusted `workflow_run` proof definition must be merged into `main` before use; GitHub loads this event's workflow definition from the default branch. It runs only after a successful `CI Pipeline` push on `main`, validating the observed workflow ID `185409165` and path `.github/workflows/ci.yml` before the App key is read. It checks out only the workflow's trusted `github.sha`, executes no PR head code or dependencies, and creates an `action_required` Check Run on the upstream main commit SHA. That check is not required by the unchanged live ruleset and has no merge effect. A separate native read token fetches the Check Run and verifies exact name, SHA, `app.id`, slug, status and conclusion. This is **not a code review** and must never conclude `success`.

Until the post-merge workflow actually runs, token creation and live App-owned Check Run remain unverified. The live ruleset is unchanged. The later `workflow_run` review evaluator, local AI qualification, canary, governance apply, and auto-merge remain future work, not claims of this foundation PR.

The eventual review workflow should be defined on `main` and triggered after `CI Pipeline` completes. It should validate the triggering workflow's ID/path, event, repository, run conclusion, unique PR association, base and exact head before reading the App key. It must never check out or execute PR code, install PR dependencies, or download PR artifacts. It should obtain bounded PR metadata and diff via GitHub API only. A separate bounded scheduled re-evaluation should cover a human approval, thread resolution, or external check arriving after CI; those events do not retrigger `workflow_run`. Evaluations for one PR should be serialized, and the final publisher should reread mutable checks/reviews/threads as well as head. The gate does not run from the bootstrap PR itself: GitHub loads `workflow_run` definitions from the default branch.

## Verdict contract

Deterministic checks require a unique open non-draft PR targeting `main`, exact current head, successful required checks on that head from their registered producers, no unresolved threads or applicable `CHANGES_REQUESTED`, bounded complete diff, and no unclassified risk. Required sensitive paths include `.github/CODEOWNERS`, `.github/governance/**`, `scripts/github/**`, production deploy-access mechanisms, credential/secret mechanisms, and destructive or irreversible migrations. A patch absent for binary/oversized files or API pagination/truncation is never silently omitted. The CODEOWNERS catch-all is narrowed so ordinary PRs do not solicit humans unnecessarily. Sensitive changes require an applicable approval by `abenrhouma` or `adammeg` on the exact head; otherwise the App posts `action_required`.

The model must emit exactly `{ "review_complete": true, "blocking_findings": [], "warnings": [], "confidence": 0.0 }` under a strict schema (typed finding objects and bounded text, no additional properties). Model unavailable, timeout, invalid output, changed head, non-green CI, and blocking findings yield `failure`. Unclassified high risk, incomplete/unsupported large diff, and a sensitive PR awaiting human approval yield `action_required`. The gate never uses `neutral`/`skipped` for missing review.

The second layer uses a pinned Apache-2.0 Qwen2.5-Coder 1.5B Instruct GGUF Q4_K_M model on a standard GitHub-hosted runner, with pinned and checksum-verified model bytes, a pinned MIT llama.cpp runtime, bounded prompt/context/time, and strict JSON schema validation. The model is an independent automated reviewer role, not a human approval. Strict JSON proves syntax only, not semantic correctness; the canary and adversarial tests must assess behavior before live ruleset activation. Cubic remains optional and non-required; its unresolved threads still block.

## Governance transition

The bootstrap PR retains the live one-human-approval ruleset. Governance-as-code declares the later target: zero routine required approvals, no last-push approval, thread resolution retained, existing required checks preserved, no bypass actors, and `Nexus Review Gate` added with the verified App ID. Because the live audit currently compares `desired` to live, it must gain an explicit, time-bounded transition state: before activation it accepts only the exact sealed legacy prestate; after activation the operator runs `--require-target` and it accepts only the exact target. Generic audit output must say which state matched, never label legacy as target-qualified. After the transition deadline legacy must fail. The apply operator must produce a prestate snapshot and dry-run, perform bounded read-modify-write, post-read exact verification and rollback on mismatch. No live application occurs before bootstrap human review, merge, post-merge CI, App source proof, and an explicit operator step.

Normal PRs arm GitHub native MERGE auto-merge only after the gate and other checks are satisfied. The minimal App has **no Pull requests permission**, so a separate trusted GitHub Actions token with narrowly scoped PR-write authority must arm auto-merge; the App token cannot do it. Sensitive PRs do not arm before applicable human approval. Branch updates require a clean/behind PR and `expected_head_sha`; conflicts and stale heads stop. Pure pre-live tests must prove SHA binding and stale-head refusal. A post-activation canary must additionally prove head A's check cannot authorize head B, B is re-reviewed, and merge is automatic without human approval.

## Operational blockers and limits

The App installation and effective permissions were verified by the owner on GitHub's installation page. The repo variables and private-key secret are configured in Actions; their values are never read into logs or artifacts. App token creation, actual Check Run source, runner-model performance, and end-to-end canary are not attested until their respective workflows execute. They must not be represented as PASS in the bootstrap PR or report.
